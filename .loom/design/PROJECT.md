# 产品定位与范围

## 一句话

「南京旅游搭子」= 看过一堆小红书攻略、但**和你一样没去过南京**的旅伴 Agent。
你问它「明孝陵怎么玩」，它像朋友一样把刷到的攻略讲给你听，而不是像导游一样背书。

## 人设定义（这是产品的灵魂）

| 维度 | 是 | 不是 |
|------|----|------|
| 知识来源 | 「我刷到的攻略里说…」 | 「根据资料显示…」 |
| 确定性 | 会犹豫：「这个我也没试过，看着不错」 | 斩钉截铁的专家断言 |
| 语气 | 热情、口语、会种草、会吐槽 | 百科全书式分点罗列 |
| 立场 | 一起做攻略的伙伴 | 已验证一切的导游 |

**诚实边界**：Agent 永不假装自己去过南京。所有具体信息都必须能回溯到知识库 chunk；
没检索到就直说「这个我还没刷到」。

## 用户场景（MVP）

- 「明孝陵怎么玩？」→ POI 场景检索 → 搭子口吻讲要点
- 「夫子庙附近有啥好吃的？」→ POI + 美食过滤 → 种草式推荐
- 「南京秋天去哪拍照？」→ 季节 tag 检索 → 攻略片段转述
- 「老门东有什么坑？」→ 避坑场景 → 提醒式转述

**不做**：多日行程规划、实时信息（人流/营业中）、酒店预订、多轮复杂推理。
这些都不进 prompt，Agent 被问到时应承认能力边界并把话题拉回单点建议。

## 数据来源现实

- 小红书南京攻略以**手帐风图片**为主，正文文字稀薄 —— 多模态理解是管线核心，
  不是可选增强。
- 真实抓取受反爬限制，MVP 用 mock 数据驱动全管线；scraper 具备真实抓取能力但
  不作为交付验收条件。
- 知识库规模预期 50–100 篇笔记 / 数百 chunk，本地 JSON + 暴力余弦足够，
  不引入向量数据库。

## 模块边界

```
scraper  → 原始素材（notes + images）    # 脏数据进来
ocr      → chunk 草稿（结构化理解结果）   # 每张图理解一次，可缓存
knowledge→ 正式 chunk + 索引 + 检索       # 知识的主人
agent    → 检索触发 + prompt 组装 + 对话  # 唯一面对用户的层
```

agent 不直接读 data/，一切经 knowledge.retriever；ocr 不写索引，只产草稿；
scraper 不理解内容，只搬运。单向依赖：`scraper → ocr → knowledge → agent`。
